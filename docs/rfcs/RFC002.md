# RFC002 — 用户可见「最近更新」（方案 A + B）

> **状态**：`[已实施]`  
> **提出日期**：2026-09-14  
> **锁定日期**：2026-09-14  
> **关联阶段**：`.phrase/phases/phase-structure-options-and-whats-new-20260914/`  
> **关联需求**：与 RFC001 同期上线时，应写入一条通俗易懂的用户向更新说明。

---

## 1. 目标

让普通人打开工具站就能知道「最近改了什么」，不依赖翻仓库文档，不堆技术术语。

---

## 2. 已锁定方案：A + B

| 代号 | 做法 | 作用 |
| :--- | :--- | :--- |
| **A** | 顶栏固定入口「最近更新」→ 弹窗时间线 | 随时可回看；有未读时显示红点 |
| **B** | 检测到本地未读的新版本时，**自动弹一次** | 保证新功能到达率 |

可选补充（本次可不做，预留）：页脚「更新记录」链接，仍打开同一弹窗。

**不采用**：仅改 `docs/CHANGELOG.md`、顶部常驻长公告条、技术向 Changelog 直接给用户看。

---

## 3. 交互与视觉

1. **入口位置**：顶栏右侧，紧邻现有「零数据驻留 / 30分钟阅后即焚」徽章，新增可点击徽章：`✨ 最近更新`。
2. **弹窗形态**：复用现有 `securityModal` 同类交互（遮罩 + 卡片 + 关闭 /「知道了」）。
3. **未读红点**：本地 `localStorage` 记录「用户已读到的版本号」；当前版本更新则显示红点。
4. **自动弹出（B）**：页面加载时若 `已读版本 < 当前版本`，自动打开弹窗一次；用户点「知道了」后写入已读版本，红点消失。
5. **列表弹窗（A）**：展示多条历史更新（时间倒序），不仅限最新一次。

---

## 4. 内容规范（用户向 vs 开发向）

| 类型 | 存放 | 读者 | 写法 |
| :--- | :--- | :--- | :--- |
| 开发变更日志 | `docs/CHANGELOG.md` | 开发者 / Agent | 可含文件、任务号、技术细节 |
| 用户可见更新 | 前端独立数据源（如 `frontend/js/whats-new.js`） | 普通用户 | 只写能感知到的变化 |

**文案原则**：

1. 一句说清「多了什么 / 哪里更好用」；
2. 禁用：API、profile、模块名、RFC 编号、假名池等术语；
3. 每条尽量短（建议 ≤ 25 字），单次版本 2～4 条；
4. 用用户语言：列名、工作表名称、勾选、脱敏 / 打码。

**RFC001 上线时的示例文案（可微调）**：

> **2026-09-14**  
> - 上传前可以自己勾选：要不要把「列名」一起脱敏  
> - 也可以勾选：要不要把「工作表名称」一起脱敏  
> - 不勾选就和以前一样，只处理表格里的内容  

---

## 5. 版本号约定

- 用户向版本号建议使用日期形式：`2026.09.14`（或与数据源中最新一条的 `version` 字段一致）。
- 无需账号体系、无需 CMS；静态前端数据即可满足本站场景。

---

## 6. 主要改动面（实施参考）

```
frontend/index.html          # 徽章入口 + 更新弹窗 DOM
frontend/css/style.css       # 红点与弹窗样式（对齐现有 modal）
frontend/js/whats-new.js     # 用户向更新列表 + 版本常量（新建）
frontend/js/app.js           # 绑定入口、未读检测、自动弹出一次
```

---

## 7. 验收标准（摘要）

1. 顶栏可点开「最近更新」，看到通俗时间线。
2. 首次（或版本升级后首次）进入会自动弹一次；点「知道了」后同版本不再自动弹。
3. 未读有红点，已读无红点；仍可从入口手动打开历史。
4. 文案无技术黑话；与 RFC001 同期交付时包含列名 / 工作表勾选相关说明。
