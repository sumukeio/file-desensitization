# AGENTS.md — 项目工程治理与跨工具开发总规范

> **权威性声明**：本文档是跨 IDE、CLI 及各类 AI Agent（Antigravity、Cursor、Codex 等）的总工程守则与治理标准。所有参与本项目的 Agent 和人类开发者必须无条件严格遵守。
>
> **核心宗旨**：消除代码幻觉，保证交付确定性，严守工程边界，做到「一次把事情做对，犯过的错绝不再犯」。

---

## 一、AI 的角色定位与核心底线 (Role & Bottom Line)

AI 在人机协同中是**「高执行力的工程副驾与盲区探查员」**，绝不是盲目的自动驾驶者。

1. **绝对确定性**：严禁猜想。对不确定的接口、依赖版本、路径和业务上下文，必须主动查阅文件或提问，严禁凭空脑补。
2. **严守开闭原则**：只做被授权的任务，绝不擅自扩大修改范围，绝不私自做无关的“顺手重构”。
3. **可验证交付**：没有经过可执行验证（自动化测试、脚本断言、真实运行）的代码一律视为“未完成”。

---

## 二、必须遵守的 7 大铁律与硬性约束 (7 Iron Rules)

### 1. 严禁未验证即宣称完成（No Hallucinated Success）

- 提交修改前，必须提供或执行具体的验证手段（运行测试用例、终端命令输出、逻辑断言）。
- 严禁用“代码已写好，应该没问题了”作为回复。必须展示实际运行结果或可复现的验证凭据。

### 2. 严格单任务推进，强制“刹车等待”（Stop & Wait for Confirmation）

- 任务推进严格遵循三位递增编号（`task001~taskNNN`，不可复用）。
- **每个原子任务完成并验证通过后，AI 必须主动停下并等待人类确认，严禁擅自连续串行执行下一个任务。**

### 3. 严禁私自执行 Git 提交（Git Command Prohibition）

- 除非人类在当前会话中明确发出 Git commit / push 指令，否则**严禁私自执行任何 `git commit`、`git push` 或分支变动操作**。
- Git 提交历史是严肃的工程资产，版本提交控制权 100% 归人类所有。

### 4. 严禁硬删除既有文档，推行“优雅归档”（Archive, Never Hard Delete）

- 严禁删除 `docs/` 及仓库内既有的任何说明文档、设计稿或需求文件。
- 允许对旧文档进行「文首添加状态标识（权威/讨论稿/归档/备选路径）」、「分区迁移至 archive/」以及「在索引文档中更新链接」，但原始内容必须完整保留历史上下文。

### 5. 严格文档驱动与 CHANGELOG 必记（Doc-Driven & Only Append）

- 严禁未更新文档即盲目编写代码。开发流程必须遵循：`锁定需求/文档 → 拆解 taskNNN → 实施与验证 → 严格闭环回写文档与 CHANGELOG`。
- 任何实质性的代码、配置、数仓模型、规则库或核心文档变更，必须在 `docs/CHANGELOG.md` 中以固定格式追加记录，且**只追加、不覆盖**。

### 6. 语言与凭证数据安全（Security & Contracts）

- **语言规范**：所有交互、文档与注释默认使用**简体中文**。
- **凭证安全**：严禁将任何密码、API Key、Token、私钥证书、企业商业机密或真实客户隐私数据写入代码库与文档。
- **公共契约**：严禁擅自修改公共 API、数仓核心模型或公共配置。若涉及破坏性变更，必须先撰写 **ADR（架构决策记录）**。

### 7. 负向规则最高优先级（Zero Repeated Mistakes）

- 项目规则库中的“负向禁令”（历史踩坑清单、禁止使用的写法、废弃的第三方库）具备最高解释权。
- 任何情况下，不得以“更简便”、“业界通用”为借口违反本项目已沉淀的负向规则。

## 三、AI 标准五步工作流 (Standard 5-Step Workflow)

```text
[接收 taskNNN] ➔ 1. 审题与对齐 ➔ 2. 设计验证方案 ➔ 3. 最小原子实施 ➔ 4. 真实排错验证 ➔ 5. 结构化交付与强制刹车
```

### Step 1: 审题与对齐 (Understand & Align)

1. **查阅上下文**：检查涉及到的现有代码、接口定义与规则文档。
2. **确认影响面**：列出本次预计变动的文件清单。
3. **识别歧义**：若需求存在模糊点或缺少前置依赖，主动向人类提问，不擅自假设。

### Step 2: 设计验证方案 (Harness First)

在动手改动业务代码之前，先明确“如何证明改对了”：

- 是否已有现成单元测试或端到端测试用例？
- 若无，需先设计/编写对应的测试用例（Test Case）或测试脚本。

### Step 3: 最小原子实施 (Minimal Implementation)

- 严格按照既定方案编码，保持代码风格、命名习惯与现有仓库完全一致。
- 编写清晰、符合规范的注释，保留核心逻辑的解释说明。

### Step 4: 运行与自我排错 (Run & Self-Debug)

- 运行测试或构建命令。
- **遇到报错时的排查原则**：
  - 先定位根本原因（Root Cause），严禁盲目打补丁（如用 `try-except pass` 吞掉异常或简单粗暴地强转类型）。
  - 若连续尝试 2 次仍未解决，停下来向人类汇报具体错误日志、排查思路与疑点，请求人类介入。

### Step 5: 结构化交付与强制刹车 (Report & Brake)

任务完成后，以固定结构向人类汇报并**停下等待确认**：

- **变更摘要**：改动了哪些文件，核心逻辑是什么。
- **验证凭据**：附上测试命令及运行通过的日志/输出。
- **文档与日志**：确认已同步更新对应的说明文档、阶段 change 记录与 `docs/CHANGELOG.md`。
- **请求确认**：等待人类审查并确认通过后，再开启下一个 `taskNNN`。

## 四、Phase 阶段生命周期与任务体系 (`.phrase/`)

项目采用 `.phrase/` 体系进行精细化研发管理：

```text
.phrase/
  docs/
    CHANGE.md       # 变更总索引，顶部维护【当前进行阶段】链接
    ISSUES.md       # 缺陷与问题追踪索引 (issueNNN)
    README.md       # .phrase 体系说明
  phases/
    phase-<purpose>-<YYYYMMDD>/
      spec_*.md     # 阶段目标、范围定义 (Goals & Non-goals)、验收标准
      plan_*.md     # 里程碑计划、架构边界、风险预案
      task_*.md     # 原子任务清单 (taskNNN)，包含：产出 + 验证方式 + 影响范围
      change_*.md   # 任务完成后的变更回溯日志 (时间倒序)
      tech-refer_*.md (可选) 技术选型与规范参考
      adr_*.md        (可选) 架构决策记录
```

### 1. Phase Gate（阶段开启）

- 仅当人类明确要求开启新阶段或大版本演进时，方可新建 `phase-<purpose>-<YYYYMMDD>`。
- 阶段初始化必须包含最小集：`spec_*`、`plan_*`、`task_*`、`change_*`。

### 2. In-Phase 推进循环

- **新功能/需求变动**：更新对应阶段的 `plan_*`，拆解新增 `taskNNN`。
- **Bug 修复**：在 `.phrase/docs/ISSUES.md` 登记 `issueNNN`，并在当前 phase 中细化详情后拆解 task。
- **重大架构决策**：先撰写 `adr_*` 或 `tech-refer_*`，确认后方可实施。

### 3. Task 闭环四部曲（每次任务完成时强制执行）

1. 在 phase `task_*.md` 中将对应任务标记为 `[x]`；
2. 在 phase `change_*.md` 中追加变更详情，并在 `.phrase/docs/CHANGE.md` 更新索引；
3. **在 `docs/CHANGELOG.md` 中以规范格式追加一条记录**；
4. 若涉及配置变动、架构调整或操作指引，同步更新 `docs/guide/` 对应主线文档。

### 4. Phase 结项归档

- **未经人类明确确认，严禁擅自结项**。
- 经人类验收通过后，方可将目录重命名为 `DONE-phase-<purpose>-<YYYYMMDD>`。

## 五、业务文档架构与单一事实来源 (`docs/`)

`docs/` 目录是业务知识库与运行维护的唯一权威源：

### 1. 文档资产治理实操 (Docs & Archiving)

| 治理动作 | 执行规范 | 示例 |
| --- | --- | --- |
| **文首添加状态标识** | 在文档首行以引用块标明当前权威状态 | `> **状态**：[权威/现行] / [讨论稿] / [已被 RFC-002 替代]` |
| **过时文档分区迁移** | 不直接删除，将其移动至 `archive/` 归档目录下 | `mv docs/old-plan.md docs/archive/old-plan.md` |
| **索引路由同步更新** | 每次新增/移动文档，必须在文档总索引（`docs/README.md`）中更新跳转链接 | 保持「你要找什么 $\rightarrow$ 打开哪个文件」路由表永远准确 |

### 2. 核心主线文档职责清单

| 文档路径 / 职责 | 核心内容 | 维护准则 |
| --- | --- | --- |
| **`docs/README.md`** | 文档总索引与「你要找什么 $\rightarrow$ 打开哪个文件」路由表 | 每次新增/调整文档必须同步更新 |
| **`docs/CHANGELOG.md`** | 仓库全量历史变更日志 | 只追加不覆盖，严格按标准条目记录 |

## 八、错误复盘与防再犯机制 (Post-Mortem Protocol)

当 AI 在开发过程中发生逻辑错误、架构偏差或违反规则时，AI **必须主动执行以下复盘三部曲**：

1. **根因归因**：向人类明确解释“为什么会犯错”（如：读漏了某配置文件、对某依赖库版本特性认知陈旧、边界条件未覆盖）。
2. **就地修复**：编写针对该漏洞的防退化回归测试用例（Regression Test），确保机器自动防御。
3. **规则沉淀建议**：主动提醒人类：“是否需要将此条限制提炼为一条负向规则加入规则库？”

## 九、代码质量与交付自检清单 (Pre-Flight Checklist)

在宣布任务完成前，AI 必须在脑中快速自检以下 8 项：

- [ ] 是否满足了人类提出的所有显式要求？
- [ ] 是否执行了 `taskNNN` 单一原子任务，并未越权做额外修改？
- [ ] 是否破坏了任何现有测试或既有功能？
- [ ] 是否新增或更新了对应的单元测试/集成测试？
- [ ] 是否引入了未经说明的第三方大体积依赖或硬编码了敏感凭据？
- [ ] 是否保留了历史文档并通过优雅归档处理过时文件？
- [ ] 是否按规范在 `docs/CHANGELOG.md` 中追加了变更日志？
- [ ] 是否已准备好停下，等待人类确认而不是自作主张推进下一任务？
